# Сценарий сессии на 90 минут

`S` ниже — `python3 <skill>/scripts/session.py`, запуск из корня рабочей папки сессии.
Все отчёты — в `reports/`; открывайте их в просмотрщике markdown, а не в сыром терминале.

| Время | Блок | Вау-момент | Команды |
|---|---|---|---|
| 0–10 | Крючок | Нарушения его стандарта в его коде за 30 секунд | `S check --top 10` |
| 10–25 | Как это получилось | Он сам превращает требование в проверку | промпт P3, `S check --top 10` |
| 25–40 | Кодовый агент | Тесты зелёные — стандарт нарушен — проверка ловит | заранее готовый эксперимент P5 |
| 40–55 | Стандарт как продукт | Он выпускает новую версию и видит весь флот | `S fleet bump`, `S fleet report` |
| 55–70 | Честная часть | Сам находит лазейку, видит её закрытие | `S bypass`, `S selftest` |
| 70–85 | Его пилот | Заполняет план пилота сам | `work/pilot-canvas.md` |
| 85–90 | Итог | Уходит с файлами на руках | `S pack` |

## 0–10. Крючок

Никаких слайдов о Spine. Первая фраза:

> Перед встречей я взял ваш «<стандарт>» из Confluence и <N> репозиториев вашего домена.
> Давайте посмотрим, что получилось.

```bash
S check --top 10
```

Открыть `reports/check.md`. Показать строку со ссылкой на пункт стандарта.

Сказать: «Это не мнение модели, а программа: одинаковый результат при каждом запуске.
Каждая строка ссылается на пункт вашего стандарта».

## 10–25. Как это получилось

1. Показать цепочку: страница стандарта → `work/requirements.md` (классы A/B/C) →
   `work/CONSTRAINTS.corp.yaml` (у каждого правила `std_ref`).
2. Обратить внимание на долю классов: сколько требований проверяемо, сколько только человеком,
   какие помечены «неоднозначно» — это находка о самом стандарте.
3. Архитектор **сам** выбирает требование класса A без правила и вводит промпт P3.
4. `S check --top 10` — новое правило уже находит (или честно не находит) нарушения.

Сказать: «Вы делаете то же, что и раньше: отдаёте стандарт агенту. Но результат теперь не только
документ, который кто-то должен прочитать, но и проверка, которая работает сама».

Страховка: заранее проверенное запасное требование, для которого правило точно срабатывает.

## 25–40. Кодовый агент и зелёные тесты

Показать заранее проведённый эксперимент P5: рука A (только `architecture.md`) и рука B
(правила доступны агенту). В руке A тесты зелёные, стандарт нарушен; проверка находит это
одной командой. Если есть время — перезапустить проверку вживую:

```bash
S check --rules work/CONSTRAINTS.corp.yaml
```

Сказать: «Ваш architecture.md для агента — просьба. Правило — проверка. Просьбу агент может
проигнорировать, проверку в CI — нет».

## 40–55. Стандарт как продукт

Заранее выполнено `S fleet init` (репозитории не меняются: файлы продуктов — в `sandbox/products/`).

```bash
S fleet check                 # все продукты на текущей версии
S fleet bump                  # архитектор «выпускает» новую версию (можно --add-rules файл)
S fleet report                # отчёт ДКА по всем продуктам
S fleet repin                 # продукты осознанно переходят на новую версию
```

Лучше, если `bump` запускает сам архитектор. После `bump` каждый продукт получает находку
«родитель обновился — перепиновать осознанно».

Сказать: «Сейчас новая версия стандарта — это рассылка. Здесь она приходит в сборку каждого
продукта как находка, а вы видите, кто уже перешёл».

## 55–70. Честная часть

1. Предложить архитектору придумать, как обойти одно из его правил. Подсказка при необходимости:
   упомянуть нужное слово в комментарии. Показать `reports/selftest.md`: какие правила «хрупкие».
2. `S bypass` — три лазейки продукта (удалить `extends`, затенить правило своим пустым,
   исключение с несуществующим ADR) скрывают нарушение; эффективный файл ДКА его показывает.

Сказать: «Правила пишет агент — значит, их тоже нужно проверять, и это теперь ваша роль:
решать, каким правилам можно доверить блокировку. А правила и исключения должны принадлежать
ДКА, а не продукту».

## 70–85. План пилота

Вместе заполнить `work/pilot-canvas.md`: стандарт и 10–15 правил (с учётом selftest),
3–5 продуктов, люди (DevOps для Jenkins и Bitbucket, ИБ, два архитектора ДКА),
что замерить до старта, критерий успеха через 8–10 недель.

## 85–90. Итог

```bash
S pack
```

Архитектор получает `handout/` и архив: requirements.md, CONSTRAINTS.corp.yaml, отчёты,
план пилота. Финальная фраза:

> Раньше вашим результатом был документ, который объясняет стандарт. Теперь — ещё и проверка,
> которая показывает, соблюдается ли он.

## Если что-то пошло не так

| Ситуация | Что делать |
|---|---|
| Ноль находок | Не допускать на подготовке (preflight). Если всё же — перейти к эксперименту с дрейфом |
| Ложное срабатывание | Превратить в урок: уточнить `pattern`/`exclude_glob` — это работа архитектора с правилами |
| Упала сеть или модель | Детерминированные проверки работают без сети; LLM-шаги — по записи экрана |
| «Это не нарушение» | Значит, пункт стандарта неоднозначен — ценная находка, записать в requirements.md |
| Вопрос о промышленной готовности | Ответ из references/limits.md: что проверено, что предстоит проверить в пилоте |
