# Вау-сессия Spine Core для корпоративного архитектора

Скилл готовит и проводит встречу, на которой архитектор впервые видит **свой** стандарт
исполняемым на **своём** коде. Проверки выполняет Spine Core (`arch-be`); скрипт
`scripts/session.py` готовит входы, вызывает `arch-be` и собирает отчёты для показа.

Главная мысль, которую должна донести сессия: результат работы архитектора — не только
документ, объясняющий стандарт, но и проверка, показывающая, соблюдается ли он.

## Почему сессия устроена именно так

- **Его данные, а не учебный пример.** Собственные нарушения в собственном коде убеждают,
  учебный пример — нет. Поэтому всё строится из контекста, который кладёт архитектор.
- **Скорость и отсутствие сюрпризов.** 70% успеха — подготовка: на встрече не должно быть
  установки, сборки, ложных срабатываний и нуля находок.
- **Прослеживаемость.** Каждая находка ссылается на пункт стандарта (`std_ref`) — это самый
  сильный момент встречи.
- **Он делает сам.** Минимум два действия архитектора своими руками: промпт P3 и `fleet bump`.
- **Честность.** Лазейки показываются намеренно: доверие вызывает показанная граница,
  а не обещание, что всё защищено.

## Правила поведения агента

- **Не изменять репозитории архитектора.** Все демо-файлы — в `sandbox/` рабочей папки.
- **Всегда `--no-exec`** при проверке чужих репозиториев (скрипт делает это сам): команды
  из правил не исполняются.
- **Не отправлять код и стандарты за периметр.** Если модель внешняя — работать только
  с тем, что разрешено политикой; LLM-шаги можно выполнить заранее на разрешённой модели.
- **Не утверждать непроверенное.** Что проверено и где границы — `references/limits.md`.
- **Не ослаблять правила, чтобы тест прошёл.** Хрупкое правило — это находка, о ней сообщают.

## Рабочая папка и контекст архитектора

```bash
python3 <skill>/scripts/session.py init ~/spine-session-<домен>
cd ~/spine-session-<домен>
```

Структура после `init`:

```
context/session.yaml       # КТО, КАКОЙ стандарт, КАКИЕ репозитории — заполняет архитектор
context/standard/          # экспорт страниц Confluence (md/html/txt), кукбуки, референсы
context/architecture.md    # необязательно: его сгенерированный architecture.md
context/exceptions.yaml    # демо-реестр исключений ДКА
work/requirements.md       # требования с классами A/B/C (генерирует агент, проверяет архитектор)
work/CONSTRAINTS.corp.yaml # корпоративный слой правил (генерирует агент)
work/rules-tests/          # примеры bad/good/bypass для проверки надёжности правил
work/pilot-canvas.md       # план пилота на одной странице
reports/                   # отчёты для показа
sandbox/                   # демо-файлы флота и лазеек; репозитории не трогаются
handout/                   # раздаточный пакет
```

Попросите архитектора заполнить `context/session.yaml` (шаблон с комментариями) и положить
экспорт стандарта в `context/standard/`. Если он не знает, какой стандарт выбрать, предложите
тот, что соблюдается хуже всего по его ощущениям: техрадар, интеграционный стандарт (границы
доменов), требования к секретам и безопасности интеграций. Репозитории: 3–5 из его домена,
склонированные заранее, доступ на чтение.

Бинарь Spine Core: `arch-be` из PATH, либо путь в `spine.arch_be`, либо переменная `ARCH_BE`.
Нужна release-сборка: debug-сборка на больших репозиториях очень медленная.

## Репетиция перед первой сессией

Прогоните весь сценарий на демо-данных, не трогая контекст архитектора. Нужен клон
репозитория Spine (из него берутся учебные репозитории):

```bash
python3 <skill>/scripts/session.py init ~/spine-rehearsal --demo ~/src/spine-bank
cd ~/spine-rehearsal
python3 <skill>/scripts/session.py preflight
python3 <skill>/scripts/session.py check
python3 <skill>/scripts/session.py selftest
python3 <skill>/scripts/session.py fleet init
python3 <skill>/scripts/session.py fleet bump --add-rules work/new-rules.yaml
python3 <skill>/scripts/session.py fleet report
python3 <skill>/scripts/session.py bypass
```

Ожидаемо: 5 находок по трём репозиториям, одно правило «надёжно» и три «хрупко»
(включая обход техрадара переименованием зависимости в Cargo), после `bump` все продукты
получают «родитель обновился», в `bypass` три лазейки скрывают нарушение, эффективный файл
ДКА его показывает.

## Этап 1. Подготовка (до встречи)

Выполняйте по порядку. Промпты — в `references/prompts.md`, поля правил — в `references/rules.md`.

1. **Стандарт → требования.** Промпт P1 → `work/requirements.md`. Архитектор проверяет
   классы A/B/C — таблицу проверить быстрее, чем документ.
2. **Требования → правила.** Промпт P2 → `work/CONSTRAINTS.corp.yaml`: `version`, у каждого
   правила `std_ref` и `rationale` со ссылкой на пункт, `severity: warn`; класс C —
   `unverifiable: true` с `owner`. В `glob` — списки, без фигурных скобок.
3. **Предполётная проверка:**
   ```bash
   python3 <skill>/scripts/session.py preflight
   ```
   Отчёт `reports/preflight.md`. Цель — 5–30 понятных находок (коридор в `tuning`).
   Ноль — сменить правила или репозитории. Слишком много — показывать `--top 10`.
4. **Вычистить ложные срабатывания:**
   ```bash
   python3 <skill>/scripts/session.py check
   ```
   Пройти `reports/check.md` вместе с архитектором или сами; уточнить `pattern`,
   `exclude_glob`. Одно ложное срабатывание на встрече подрывает доверие ко всему.
5. **Надёжность правил:** промпт P4, затем
   ```bash
   python3 <skill>/scripts/session.py selftest --scaffold   # каталоги примеров
   python3 <skill>/scripts/session.py selftest              # таблица надёжности
   ```
   Хотя бы одно правило должно оказаться «хрупким» — это материал для блока 55–70.
6. **Флот и лазейки:**
   ```bash
   python3 <skill>/scripts/session.py fleet init
   python3 <skill>/scripts/session.py fleet check
   python3 <skill>/scripts/session.py bypass
   ```
   `bypass` сам выбирает правило с находкой; можно указать `--repo` и `--rule`.
   После прогона выполните `fleet init` снова, чтобы на встрече начать с чистой версии.
7. **Эксперимент с дрейфом:** промпт P5, две руки в изолированных копиях, результаты и запись
   экрана — заранее.
8. **Страховка:** запасное требование для живого шага P3; записи экрана каждого блока.

Готовность к встрече: preflight без проблем, ложные срабатывания разобраны, есть хрупкое
правило, `bypass` показывает «СКРЫТО → видно», эксперимент с дрейфом записан.

## Этап 2. Сессия (90 минут)

Подробные реплики и страховки — `references/scenario.md`. Кратко:

| Время | Блок | Команда |
|---|---|---|
| 0–10 | Крючок: нарушения его стандарта в его коде | `session.py check --top 10` → `reports/check.md` |
| 10–25 | Он сам превращает требование в проверку | промпт P3 → `session.py check --top 10` |
| 25–40 | Кодовый агент: тесты зелёные, стандарт нарушен | заранее готовый эксперимент P5 |
| 40–55 | Стандарт как продукт: версия и весь флот | `session.py fleet bump` → `fleet report` → `fleet repin` |
| 55–70 | Честная часть: хрупкие правила и лазейки | `reports/selftest.md`, `session.py bypass` |
| 70–85 | План пилота | `work/pilot-canvas.md` |
| 85–90 | Итог | `session.py pack` |

Не показывайте TUI Spine, рубрики, бенчмарки и Jenkins-пайплайн: каждая лишняя функция
размывает главную мысль. Не начинайте с теории — объясняйте после вау-момента.

## Этап 3. Итог

```bash
python3 <skill>/scripts/session.py pack
```

В `handout/` и архиве `handout-spine-session.zip`: requirements.md, CONSTRAINTS.corp.yaml,
отчёты (preflight, check, fleet, bypass, selftest), план пилота и README.

Следующий шаг после встречи — пилот защищённого реестра корпоративных правил с гейтом
в CI (Jenkins + Bitbucket): правила, исключения и гейт принадлежат ДКА, корпоративный слой
проверяется по эффективному файлу (`session.py effective`), а не по продуктовому.

## Команды session.py

| Команда | Что делает | Вызов Spine Core |
|---|---|---|
| `init <dir> [--demo SPINE_REPO]` | Рабочая папка из шаблонов или для репетиции | — |
| `preflight` | Окружение, контекст, коридор находок, правила без находок | `arch-be --version`, `control check --json` |
| `check [--rules F] [--top N]` | Проверка репозиториев, таблица со ссылками на пункты | `control check --no-exec --json` |
| `effective` | Эффективный файл ДКА: правила ДКА + реестр исключений ДКА | — |
| `fleet init` | Корпоративный слой с версией и продукты с `extends` в `sandbox/` | — |
| `fleet check` | Состояние флота и пины версий | `control check` по продуктам |
| `fleet bump [--to V] [--add-rules F]` | Новая версия слоя + проверка флота | `control check` |
| `fleet repin` | Перепинить продукты на текущую версию | `control check` |
| `fleet report` | Отчёт ДКА по флоту | `control report --level corp --json` |
| `bypass [--repo R] [--rule N]` | Три лазейки и их закрытие эффективным файлом | `control check` |
| `selftest [--scaffold]` | Надёжность правил на bad/good/bypass | `control check` по каждому примеру |
| `pack` | Раздаточный пакет и архив | — |

Скрипт требует Python 3.9+ и PyYAML.
