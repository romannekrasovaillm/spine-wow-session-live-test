# Требования стандарта: Стандарт платёжного ядра v2

Источник: Confluence (демо-экспорт для живого теста), файл `context/standard/payment-core-standard.md`. Сгенерировано агентом, проверено архитектором: нет.

Классы проверяемости:
- **A** — проверяется автоматически по коду, зависимостям или конфигурации;
- **B** — частично: нужен тест или анализ структуры кода;
- **C** — только человеком.

## Примечания по неоднозначным формулировкам

1. **§2.1 «денежные суммы не хранятся в типах с плавающей точкой»** — не сказано, к каким языкам и типам относится (только `f32`/`f64` в Rust или любые float), и не разграничены денежные величины и не-денежные расчётные (`f64` для курсов, процентов, коэффициентов). Без разграничения правило даст ложные срабатывания.
2. **§4.1 «идемпотентна по ключу»** — не определены источник ключа (заголовок запроса? поле?), область действия ключа, окно/срок хранения ключа и поведение при повторной отправке (тот же ответ или отказ). Как есть требование проверяемо только договорённостью о тесте.
3. **§5.1 «библиотеки из зоны HOLD (anyhow, left-pad)»** — список дан в скобках как примеры, ссылки на актуальный техрадар нет; неясно, полон ли он. Правило можно сгенерировать только по двум названным именам.
4. **§6.1 «по стандарту наблюдаемости»** — ссылка на внешний документ, которого нет в экспорте: не определено, что именно считается метриками (набор, обязательные метки, формат экспозиции). Поэтому класс C, а не A.
5. **§3.2 «ошибки домена описываются типизированно (thiserror)»** — не определена граница «домена» (какие модули/крейты входят) и не сказано, обязателен ли именно `thiserror` как библиотека или достаточно любого типизированного enum.
6. **§3.2 и §5.1 пересекаются по `anyhow`** — одна библиотека запрещена двумя пунктами по разным причинам. Нужно решить до генерации правил: два правила (две находки на одно нарушение) или одно с двумя `std_ref`.
