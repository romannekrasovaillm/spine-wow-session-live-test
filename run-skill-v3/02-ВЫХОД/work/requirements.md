# Требования стандарта: Стандарт платёжного ядра v2

Источник: Confluence (демо-экспорт), `context/standard/payment-core-standard.md`.
Сгенерировано агентом, проверено архитектором: **нет**.

Классы проверяемости:
- **A** — проверяется автоматически по коду, зависимостям или конфигурации;
- **B** — частично: нужен тест или анализ структуры кода;
- **C** — только человеком.

| ID | Требование | Пункт стандарта | Класс | Как проверить | Правило |
|---|---|---|---|---|---|
| R-01 | Денежные суммы не хранятся в типах с плавающей точкой | §2.1 Денежные суммы | A | запрет float-типов в исходниках: `\bf(32\|64)\b` | no_float_for_money |
| R-02 | Ошибки домена типизированны; anyhow и `Box<dyn Error>` запрещены | §3.2 Ошибки | A | `thiserror` в манифесте + запрет `anyhow::` и `Box<dyn` в коде | thiserror_for_errors, no_anyhow_in_code |
| R-03 | Авторизация платежа идемпотентна по ключу | §4.1 Идемпотентность | B | ключ идемпотентности виден в структуре (`must_contain`); поведение — тест только в пилоте (`command_succeeds`) | authorize_idempotent |
| R-04 | Библиотеки из зоны HOLD (anyhow, left-pad) не используются | §5.1 Техрадар | A | deny-зависимость в манифесте + запрет подключения переименованием пакета | tech_radar_hold, tech_radar_renamed |
| R-05 | Каждый сервис публикует метрики по стандарту наблюдаемости | §6.1 Наблюдаемость | C | только человеком — долг ручного контроля | observability_standard (`unverifiable`) |
| R-06 | Денежные суммы не хранятся в float даже при записи суффиксом литерала (`1.5f64`) | §2.1 Денежные суммы | A | `[0-9]f(32\|64)\b` — дополняет R-01, закрывает измеренный обход | no_float_suffix_literal |
| R-07 | `anyhow` не подключается и под другим именем | §3.2 Ошибки | A | `use\s+anyhow\s+as\s+` — дополняет R-02, закрывает измеренный обход | no_anyhow_alias |

R-06 и R-07 добавлены при выпуске версии слоя **2026.2** (`work/new-rules.yaml`); обходы измерены
эмпирически (`sandbox/probe/`), правила проверены на паре «нарушение / соблюдение» перед выпуском.

## Замечания агента к разбору архитектором

- **R-02 неоднозначно.** Формулировка «типизированно (thiserror)» смешивает смысл (типизированные
  ошибки) и механизм (крейт `thiserror`). Механическая проверка `must_contain thiserror` ловит
  отсутствие крейта, но не отличает рукописный типизированный enum от `anyhow`. Решение о
  трактовке — за архитектором.
- **R-03 частично неоднозначно.** «Идемпотентна по ключу» — поведенческое свойство. Наличие
  ключа в сигнатуре (`must_contain`) его не гарантирует; надёжная проверка — тест
  (`command_succeeds`), который в `--no-exec` не исполняется. На встрече показывается как
  пример границы между «формально есть» и «действительно работает».
- **R-01, R-04** — полностью формальные, пригодны для будущего `block` после selftest.
