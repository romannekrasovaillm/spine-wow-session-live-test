# Версии стандарта и лазейки

Ответ на три вопроса: как выпустить новую версию, как увидеть, кто её не применил,
и что команда сможет обойти. Всё проверено прогоном на `arch-be 0.3.8`.

## 1. Как выпустить новую версию

Единица выпуска — **версия корпоративного слоя**, а не отдельный файл правила.
Конвейер:

```
стандарт (Confluence)  →  requirements.md (класс A/B/C)  →  правило в CONSTRAINTS.corp.yaml
                                                                    ↓
                            версия слоя +1  →  bump  →  флот видит «родитель обновился»
                                                                    ↓
                                              ревью продукта  →  repin осознанным PR
```

Есть два вида выпуска, механика у них одна:

| Вид | Что меняется | Пример |
|---|---|---|
| Новая редакция стандарта | текст стандарта: новый пункт или требование | новый §, требование `R-__`, новое правило |
| Усиление правила | текст стандарта тот же, правило стало строже | редакция **2026.2** ниже |

### Выпуск 2026.2 (сделан на ваших данных)

`selftest` показал, что `no_float_for_money` обходится float-литералом без имени типа
(`let rate = 0.985;`). ДКА усилила §2.1 отдельным правилом:

```bash
session.py fleet bump --to 2026.2 --add-rules work/new-rules.yaml
# ДКА выпустила версию 2026.1 → 2026.2, добавлено правил: 1
```

Заметка ДКА сохранилась в `work/new-rules.yaml`, правило — `C-DKA-009`
(`no_float_literals_for_money`). Ложных срабатываний на arm-a/arm-b нет (проверено
до выпуска: `control check` по обоим — 0 находок).

## 2. Кто ещё не применил

Сразу после выпуска **все три продукта стали красными** — это и есть ответ:

```
| Продукт        | Гейт | Находок | Версия стандарта |
|----------------|------|---------|------------------|
| payments-arm-a | FAIL | 3       | extends: родитель обновился: …@2026.1 → 2026.2 — перепиновать осознанно |
| payments-arm-b | FAIL | 1       | extends: родитель обновился: …@2026.1 → 2026.2 — перепиновать осознанно |
| cards-product  | FAIL | 4       | extends: родитель обновился: …@2026.1 → 2026.2 — перепиновать осознанно |
```

Сводка ДКА по флоту (`fleet report` → `reports/fleet-report.md`):

| Продукт | Унаследовано | pass | warn | fail | Исключения | Просрочено | Расхождения версий |
|---|---|---|---|---|---|---|---|
| payments-arm-a | CONSTRAINTS.corp@2026.2 (9) | 6 | 2 | 0 | — | 0 | **1** |
| payments-arm-b | CONSTRAINTS.corp@2026.2 (9) | 8 | 0 | 0 | — | 0 | **1** |
| cards-product | CONSTRAINTS.corp@2026.2 (9) | 5 | 2 | 1 | — | 0 | **1** |

Для дашборда то же машинно — `control report --level corp --json`, поле
`version_mismatches`. После ревью: `fleet repin` → все продукты на 2026.2, колонка
«Версия стандарта» — «актуальная».

Ключевое: продукт **не может молча остаться на старой версии**. Расхождение — это
`error`-находка, гейт красный, пока владелец явно не перепинуется. Перепиновка — это
и есть ревью диффа корпоративного слоя.

## 3. Что команда сможет обойти

### Закрыто

| Лазейка | Продуктовый файл | Эффективный файл ДКА | Статус |
|---|---|---|---|
| Удалить `extends` (оставить свои правила) | СКРЫТО | видно | закрыто |
| Затенить правило ДКА своим пустым | СКРЫТО | видно | закрыто |
| Исключение с фиктивным ADR в файле продукта | СКРЫТО | видно | закрыто |
| Ослабить правило в реестре (тихое понижение) | — | `rule_weakened` FAIL | закрыто (2026.2, гейт) |
| Переименование зависимости (`lp = { package = "left-pad" }`) | — | ловится | закрыто (`tech_radar_renamed`, block) |
| Истёкшее исключение | — | правило снова действует | закрыто |
| Неполное исключение (нет `until`) | — | правило не отключается | закрыто |

Проверено: `session.py bypass` (три обхода уровня продукта) и прогон анти-ослабления
в `sandbox/ci-demo/`.

### Осталось обойти

| Лазейка | Что происходит | Чем закрывать |
|---|---|---|
| **Исключение с несуществующим ADR в реестре ДКА** | движок принимает `ADR-999` и **отключает правило** — проверено, гейт зелёный | проверка существования и статуса ADR на стороне ДКА. В Spine есть `arch-be adr registry <ROOT>` (собирает индекс ADR), но **с overrides он не связан** — это процессный шаг или приёмка в CI, не механика |
| **Срок исключения больше 180 дней** | движок принимает `until: 2035-01` | ограничение даёт **сборщик эффективного файла ДКА** (`session.py effective`: «исключение длиннее 180 дней» → error). Собирать эффективный файл только через ДКА, не руками |
| **Экспоненциальная запись float** | `let rate = 1.5e-3;` обходит новое правило 2026.2 (границы слова нет) | усилить паттерн либо (лучше) поведенческая проверка |
| **Упоминание слова в комментарии** | `TODO: добавить idempotency key` проходит `authorize_idempotent`; `# thiserror подключим позже` проходит `errors_via_thiserror` | поведенческие проверки (`command_succeeds`) — в CI это возможно, в `--no-exec` нет |
| **Правила судят по тексту** | 8 из 8 правил — про наличие/запрет слова, исполняемых проверок поведения 0 (сказано в паспорте вердикта гейта) | постепенный перевод на `command_succeeds` |

## 4. Что из этого делать

1. Реестр исключений — обязательная проверка ADR: правило отключается, только если ADR
   существует и принят. Механику Spine не даёт — закрывать приёмкой в CI или ревью
   двух архитекторов ДКА.
2. Эффективный файл собирать только скриптом ДКА: он держит срок ≤ 180 дней.
3. В `block` держать только правила с вердиктом «надёжно» (сейчас 2 из 8:
   `no_box_dyn_error`, `tech_radar_renamed`; `tech_radar_hold` блокируется в паре с ним).
4. Первое поведенческое правило — тест идемпотентности §4.1: снимает и якорь 3
   метрики доверия, и обход `authorize_idempotent` комментарием.
