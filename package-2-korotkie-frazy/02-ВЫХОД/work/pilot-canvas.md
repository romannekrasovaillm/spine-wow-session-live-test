## 5. Успех через 8–10 недель — это…

1. Гейт ДКА работает в Jenkins на каждом MR трёх продуктов, статус обязателен для
   слияния в Bitbucket; реестр правил живёт в репозиториях под default reviewers ДКА
   — проверено, что попытка ослабить правило валит сборку (`reports/ci-gate.md`).
2. Все правила из `warn` переведены в `block` **осознанно**: по каждому снят bypass
   из `work/rules-tests/` и есть поведенческая проверка.
3. Появились поведенческие правила (`command_succeeds`), которых сейчас **0 из 8**:
   первое — тест идемпотентности §4.1; это снимает якорь 3 метрики доверия.
4. `arch-be trust` вырос с 1 из 5: закрыты «Контур подключён» и «Правила сопровождаются».
5. Baseline по старому долгу зафиксирован; новые нарушения ломают сборку, старые — нет.

### Следующий шаг после встречи

Отдельный репозиторий ДКА с реестром правил, реестром исключений и `ci/gate.sh`;
продукты подключают его как `.arch-handoff/CONSTRAINTS.yaml` (копия, принадлежащая
ДКА) — тогда корпоративный слой проверяется по эффективному файлу, а не по продуктовому.

Обязательно закрыть две процессные дыры (механикой Spine не закрыты, проверено —
`reports/versioning-and-bypass.md`):

1. **Проверка ADR в реестре исключений.** Движок принимает исключение с несуществующим
   `ADR-999` и отключает правило. Нужна приёмка в CI (`arch-be adr registry` собирает
   индекс ADR, но с `overrides` не связан) или ревью двух архитекторов ДКА.
2. **Срок исключения ≤ 180 дней** обеспечивает только сборщик эффективного файла ДКА,
   не движок. Эффективный файл собирать исключительно скриптом ДКА.

Порядок выпуска новой версии: правка стандарта → `requirements.md` → правило в реестре
ДКА → `fleet bump` (продукты видят «родитель обновился», гейт красный) → ревью →
`fleet repin`. Продукт не может молча остаться на старой версии.
