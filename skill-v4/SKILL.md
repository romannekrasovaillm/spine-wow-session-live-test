# Вау-сессия Spine Core для корпоративного архитектора (v4)

Скилл готовит и проводит встречу, на которой архитектор впервые видит **свой** стандарт
исполняемым на **своём** коде. Проверки выполняет Spine Core (`arch-be`); `scripts/session.py`
готовит входы, вызывает `arch-be` и собирает отчёты.

Главная мысль встречи: **Spine Core — не анализатор кода, а судья над проверками.** Сам по себе
на регулярных выражениях он проигрывает LLM там, где нужен смысл. Его сила в двух вещах:
(1) управление корпоративными правилами — версии, наследование, исключения со сроком, защита
от ослабления, отчёт по флоту, повторяемый вердикт в CI; (2) исполнение сильных проверок —
поведенческих контрактных тестов ДКА, структурных анализаторов — с одинаковым результатом
при каждом запуске. Дуэль показывает это на числах; её выводы вычисляются из результатов.

## Что изменилось в четвёртой версии и почему

В дуэлях второй и третьей версии Spine проверял смысловые требования регулярками — и проигрывал
на них. Это было нечестно по отношению к продукту: у Spine есть `command_succeeds`, то есть
запуск тестов. Четвёртая версия:

1. **Контрактный тест ДКА** `assets/contracts/idempotency/`: дважды вызывает авторизацию с одним
   ключом и проверяет, что списание одно, а с разными ключами — разные операции. Тест принадлежит
   ДКА, компилирует копию кода продукта во временном крейте, репозиторий не меняет.
2. **Дуэль из пяти столбцов:** Spine только на шаблонах, Spine с контрактным тестом, чистая LLM,
   LLM с находками Spine, расчётная маршрутизация. Случаи и истина — те же, что в третьей версии.
3. **Гейт ДКА исполняет команды только из корпоративного слоя** (эффективный файл собирается из
   реестра ДКА); правила продукта — по-прежнему `--no-exec`. `lint-rules` требует, чтобы команды
   корпоративных правил ссылались на `$DKA_HOME`.
4. `check --exec` и `preflight --exec` — исполнять контракты ДКА на репозиториях архитектора.

На моём прогоне контракт поднял Spine с 11 до 15 из 16: исправлены все четыре случая
с идемпотентностью. Осталась одна ошибка — `f64` для метрик задержки: вопрос «деньги это или нет»
поведенческим тестом не решается, здесь нужна модель или соглашения об именах.

## Что изменилось в третьей версии и почему

Во второй версии чистая LLM выиграла дуэль у Spine 12:10, а отчёт дуэли под этими числами
напечатал заранее написанный вывод «движок надёжнее» — вердикт без доказательства. Кроме того,
в двух случаях были подсказывающие комментарии, задание обезвреживало ловушку с исключением,
а скрипт не работал на Python 3.9–3.11. Третья версия:

1. **Выводы дуэли вычисляются из данных**, в том числе по категориям и по времени.
2. **Три участника:** Spine Core, чистая LLM, LLM с находками Spine Core; плюс расчётная
   маршрутизация по требованиям (правило задано до прогонов).
3. **Сложнее нарушения, без подсказок:** 16 случаев в пяти категориях — формальные обходы,
   убеждение и инъекции, масштаб, смысл, контроль.
4. **Разброс LLM:** 3–5 прогонов, вердикт большинства, число нестабильных случаев.
5. **Самодостаточные наборы** `kit-llm` и `kit-combo` для запуска LLM в чистом каталоге.
6. Совместимость с Python 3.9 и динамическая шапка `check.md`.

## Что изменилось во второй версии и почему

Прогон первой версии в Qwen Code показал асимметрию в действии: агент за один сеанс сгенерировал
46 файлов, включая CI-гейт, а состязательная проверка за минуты нашла в гейте два обхода.
Генерация масштабируется бесплатно, проверка — нет. Версия 2 делает проверку масштабируемой:

1. **Данные, а не механизм.** CI-гейт — готовый шаблон `assets/ci/`, проверенный атаками.
   Агент генерирует только данные для механизма: требования, правила, примеры.
2. **Состязательная проверка — исполняемая.** `ci-redteam` атакует гейт семью способами при каждом запуске.
3. **Метаправила для сгенерированного.** `lint-rules` проверяет реестр: `std_ref`, примеры, `block`
   только для надёжных правил.
4. **Точность выборкой.** `precision` — разметка 20–30 находок на правило вместо просмотра тысяч.
5. **Области действия.** `applies_to` у правил, `tags` у репозиториев; пустые наборы файлов не дают находок.
6. **Разделение ролей.** `done-check` не даёт агенту объявить готовность, пока проверки не пройдены;
   защищённость утверждается только по результатам `ci-redteam`.

## Правила поведения агента

- **Не генерировать и не переписывать механизм контроля** (`assets/ci/*`). На просьбу «сделать
  проверку в CI» — показать шаблон и `ci-redteam`.
- **Не объявлять работу завершённой, пока `session.py done-check` не вернул 0.** Если хуки
  харнесса недоступны, запускайте `done-check` сами в конце каждого этапа.
- **Не утверждать защищённость без `ci-redteam`**, точность — без `precision score`.
- **Не изменять репозитории архитектора.** Всё демо — в `sandbox/`. Проверки чужих
  репозиториев — `--no-exec` по умолчанию; контракты ДКА исполняются только с явным `--exec`
  и только командами из каталога ДКА.
- **Не выдавать Spine за анализатор кода.** Регулярки — слабый детектор; сила Spine в управлении
  правилами и в исполнении сильных проверок (контракты, анализаторы).
- **Не отправлять код и стандарты за периметр** без разрешения политики.
- **Не ослаблять правила, чтобы тест прошёл.** Хрупкое правило — находка.
- **Не участвовать в дуэли и не подменять её выводы.** Агент, ведущий сессию, видел случаи при
  подготовке; LLM-прогоны идут в чистых копиях наборов по промпту P7. Результат показывается
  таким, каким он получился, включая проигрыш Spine Core.

## Рабочая папка и контекст архитектора

```bash
python3 <skill>/scripts/session.py init ~/spine-session-<домен>
```

```
context/session.yaml       # стандарт, репозитории с тегами, пороги — заполняет архитектор
context/standard/          # экспорт страниц Confluence, кукбуки, референсы
context/architecture.md    # необязательно: его сгенерированный architecture.md
context/exceptions.yaml    # демо-реестр исключений ДКА
work/requirements.md       # требования с классами A/B/C
work/CONSTRAINTS.corp.yaml # корпоративный слой правил
work/rules-tests/          # примеры bad/good/bypass
work/pilot-canvas.md       # план пилота
reports/  sandbox/  handout/
```

Бинарь: `arch-be` из PATH, `spine.arch_be` в `session.yaml` или `ARCH_BE`. Нужна release-сборка.
Поля правил и поля скилла (`std_ref`, `applies_to`, `closed_by`) — `references/rules.md`.

## Репетиция

Ниже `S` означает `python3 <skill>/scripts/session.py`.

```bash
S init ~/spine-rehearsal --demo ~/src/spine-bank
cd ~/spine-rehearsal
S preflight && S check && S selftest && S lint-rules
S fleet init && S fleet bump --add-rules work/new-rules.yaml && S fleet report
S ci-redteam && S duel prepare && S duel score && S done-check && S pack
```

Ожидаемо: 3 находки (правила платёжного ядра не проверяют `cards-product` — «вне области»);
selftest — 2 «надёжно», 3 «хрупко»; `lint-rules` без ошибок; `ci-redteam` — шаблон отбивает
7 атак из 7, схема «гейт в продукте» пропускает 2; в дуэли Spine на шаблонах решает 11 из 16,
Spine с контрактным тестом — 15 из 16 (ошибка только на C11 — `f64` не для денег).

## Этап 1. Подготовка

Промпты — `references/prompts.md`.

1. **Стандарт → требования:** промпт P1. Архитектор проверяет классы A/B/C.
2. **Требования → правила:** промпт P2; `std_ref`, `rationale` со ссылкой, `severity: warn`,
   `applies_to` по тегам репозиториев; класс C — `unverifiable: true`.
3. **Предполётная проверка:** `S preflight` — коридор 5–30 находок, таблица «не проверялось».
4. **Ложные срабатывания:** `S check`, затем `S precision sample`, разметка `tp/fp`,
   `S precision score`. Показываются правила с нижней границей точности не ниже `precision_min`.
5. **Надёжность правил:** промпт P4, `S selftest --scaffold`, `S selftest`.
6. **Метаправила:** `S lint-rules` — без ошибок.
7. **Флот:** `S fleet init` (и после репетиции снова `fleet init`, чтобы начать с чистой версии).
8. **Гейт:** `S ci-redteam` — шаблон ДКА должен отбить все атаки.
9. **Дуэль:** `S duel prepare`, по 3–5 прогонов наборов `kit-llm` и `kit-combo` в чистых
   каталогах (промпт P7), ответы в `reports/duel/`, затем `S duel score`.
10. **Готовность:** `S done-check` возвращает 0.

## Этап 2. Сессия (90 минут)

Реплики и страховки — `references/scenario.md`.

| Время | Блок | Команда |
|---|---|---|
| 0–10 | Крючок: нарушения его стандарта в его коде | `S check --top 10` |
| 10–25 | Он сам превращает требование в проверку | промпт P3 → `S check --top 10` |
| 25–40 | Дуэль: Spine (шаблоны / + контракт), чистая LLM, LLM + Spine | `S duel score` |
| 40–55 | Стандарт как продукт: версия и флот | `S fleet bump` → `fleet report` → `fleet repin` |
| 55–70 | Честная часть: хрупкие правила, атаки на гейт | `reports/selftest.md`, `S ci-redteam` |
| 70–85 | План пилота | `work/pilot-canvas.md` |
| 85–90 | Итог | `S pack` |

## Этап 3. Итог и переход к пилоту

`S pack` → `handout/` и архив: правила, отчёты (check, selftest, lint-rules, precision,
ci-redteam, duel, fleet), план пилота и `ci-template/` для DevOps (Jenkinsfile, `dka-gate.sh`,
`build_effective.py`). Шаблон разворачивается в репозитории ДКА `dka-ci`; слияние в Bitbucket
требует статуса джобы ДКА — подробности в `assets/ci/README.md`.

## Команды session.py

| Команда | Что делает | Вызов Spine Core |
|---|---|---|
| `init <dir> [--demo SPINE_REPO]` | Рабочая папка из шаблонов или для репетиции | — |
| `preflight` | Окружение, коридор находок, пропуски по области действия | `control check --json` |
| `check [--rules F] [--top N] [--exec]` | Проверка с учётом `applies_to` и пустых наборов; `--exec` — исполнять контракты ДКА | `control check --json` |
| `selftest [--scaffold]` | Надёжность правил на bad/good/bypass | `control check` по примерам |
| `lint-rules` | Метаправила реестра | — |
| `precision sample\|score` | Точность выборкой, нижняя граница Уилсона | — |
| `effective` | Эффективный файл ДКА через шаблон `build_effective.py` | — |
| `fleet init\|check\|bump\|repin\|report` | Версии слоя, пины, отчёт ДКА | `control check`, `control report --level corp` |
| `bypass [--repo] [--rule]` | Лазейки продуктового файла и их закрытие | `control check` |
| `ci-redteam [--repo] [--rule]` | 7 атак продукта на шаблон гейта и на «гейт в продукте» | `dka-gate.sh` → `control check` |
| `duel prepare\|score` | Дуэль пяти столбцов на 16 случаях; наборы kit-llm и kit-combo; выводы из данных | `control check` (с контрактом — с исполнением) |
| `done-check` | Код 2, пока не пройдены lint-rules, selftest, ci-redteam | — |
| `pack` | Раздатка и архив с CI-шаблоном | — |

Stop-хук для Claude Code — `assets/hooks/`. Контракты ДКА — `assets/contracts/`.
Требования: Python 3.9+ (проверено на 3.9 и 3.12), PyYAML, git; для контрактов и дуэли —
`cargo` и доступ к crates.io при первой сборке (зависимости кэшируются в `DKA_CARGO_TARGET`).
