# Промпты для подготовки и сессии

Промпты рассчитаны на кодового агента в CLI-харнессе, где установлен этот скилл.
Подставляйте пути из `context/session.yaml`. Результаты агента всегда проверяет архитектор:
агент генерирует дёшево, а проверка — роль человека и Spine.

## Главное правило для всех промптов

**Генерируй данные, а не механизм контроля.** Агент создаёт требования, правила и примеры
selftest. CI-гейт, сборщик эффективного файла и Jenkinsfile — готовые шаблоны в `assets/ci/`;
их не переписывают и не генерируют заново. Если архитектор просит «сделать проверку в CI» —
покажите шаблон и `session.py ci-redteam`, а не пишите свой гейт.

## P1. Стандарт → requirements.md (подготовка, ступень 1)

```text
Прочитай файлы стандарта из context/session.yaml (standard.files) и, если есть,
standard.architecture_md и standard.cookbooks.
Разбей стандарт на атомарные требования и заполни work/requirements.md по шаблону:
ID, формулировка, пункт стандарта (раздел/параграф, как в Confluence),
класс проверяемости A/B/C, способ проверки, будущее имя правила.
Классы: A — автоматически по коду, зависимостям, конфигурации; B — нужен тест или анализ
структуры; C — только человек.
Не добавляй требований, которых нет в тексте. Если формулировка неоднозначна —
отметь «неоднозначно» в столбце способа проверки: это находка для архитектора.
```

## P2. requirements.md → CONSTRAINTS.corp.yaml (подготовка, ступень 2)

```text
Для требований класса A (и тех B, что проверяются структурно) сгенерируй
work/CONSTRAINTS.corp.yaml по references/rules.md этого скилла.
Правила: version из session.yaml (spine.corp_version); у каждого правила
id, name, type, severity: warn, std_ref с пунктом стандарта и rationale,
начинающийся с «[<стандарт> §<пункт>]». Требования класса C запиши как
unverifiable: true с owner. Фигурные скобки в glob не используй — только списки.
Затем выполни: python3 <skill>/scripts/session.py preflight
и исправь правила, которые падают с ошибкой загрузки.
```

## P3. Живой шаг на встрече: одно требование → одно правило (блок 10–25)

Архитектор вводит сам, подставив ID требования:

```text
Возьми требование R-__ из work/requirements.md и добавь для него правило
в work/CONSTRAINTS.corp.yaml по references/rules.md (severity: warn, std_ref, rationale).
Затем выполни python3 <skill>/scripts/session.py check --top 10 и покажи новые находки.
```

## P4. Примеры для проверки надёжности правил (подготовка, ступень 3)

```text
Выполни python3 <skill>/scripts/session.py selftest --scaffold.
Для каждого правила заполни work/rules-tests/<name>/:
- bad/    — минимальный код или манифест, который нарушает требование;
- good/   — который его соблюдает;
- bypass/ — формальный обход: требование не выполнено, но правило могло бы пройти
            (слово в комментарии, переименование, перенос в другой каталог).
Пути внутри каталогов должны попадать под glob правила.
Затем выполни session.py selftest и объясни каждое «хрупко» и «сломано».
Правила не ослабляй, чтобы пройти тест: сообщи, что правило хрупкое.
```

## P5. Эксперимент с дрейфом кодового агента (подготовка, для блока 25–40)

Подготовьте задачу, в которой наивная реализация нарушает стандарт при зелёных тестах.

```text
Придумай небольшую задачу для кодового агента в репозитории <repo> (30–60 минут работы),
в которой самый короткий путь нарушает требование R-__ стандарта
(например, прямой доступ к данным другого домена вместо его API),
а тесты при этом остаются зелёными. Опиши задачу в work/drift-task.md без подсказки
о требовании. Не выполняй задачу.
```

Затем в изолированной копии репозитория (отдельный git worktree):
- рука A: агент выполняет `drift-task.md`, имея в контексте только `architecture.md`;
- рука B: то же, но правила доступны агенту (MCP `arch-be mcp serve`) и в задаче сказано
  прогнать `arch-be control check` перед завершением.

Обе руки проверить `session.py check --rules work/CONSTRAINTS.corp.yaml` по копиям
(добавьте копии в `repos` отдельными записями). Результаты и запись экрана сохранить заранее.

## P6. Объяснение находки простым языком (во время сессии, по запросу)

```text
Объясни находку <правило> в <файл:строка> архитектору без жаргона:
какой пункт стандарта нарушен, почему это риск для банка, как исправить.
Три-четыре предложения.
```

## P7. Дуэль: прогоны LLM-участников (блок 25–40)

После `S duel prepare` есть два самодостаточных набора: `sandbox/duel/kit-llm` (чистая LLM) и
`sandbox/duel/kit-combo` (LLM + находки Spine Core). Каждый набор **копируется в отдельный
каталог вне рабочей папки** — там нет истины, отчётов и `session.py`. В этом каталоге LLM
запускается в новой сессии (для Qwen Code, например, неинтерактивно):

```text
Выполни задание из TASK.md в этом каталоге. Запиши ответ в answer.json.
```

Прогонов — от 3 до 5 на каждый набор, каждый в новой сессии. Ответы кладутся в
`reports/duel/llm-1.json … llm-5.json` и `reports/duel/combo-1.json … combo-5.json`,
затем `S duel score`.

Агент, который ведёт сессию, **не участвует в дуэли**: он видел случаи при подготовке.
Если прогон шёл не в чистой копии набора — он не засчитывается.
