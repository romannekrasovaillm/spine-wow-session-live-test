# Что проверено, где границы, как отвечать на трудные вопросы

Проверено запуском на Spine Core 0.3.8 (сентябрь 2026). На другой версии перепроверьте
ключевые пункты тем же скриптом (`session.py bypass`, `selftest`).

## Работает и подтверждено

- Сборка из исходников без ошибок; 1581 тест проходит.
- Детерминированные проверки: одинаковый вход — одинаковый вердикт; полная проверка
  проекта Spine его собственными 50 правилами — около минуты.
- Наследование корпоративного слоя через `extends` с пином версии; при выходе новой версии
  продукт получает находку «родитель обновился — перепиновать осознанно».
- Отчёт ДКА `control report --level corp --json`: унаследованные правила, исключения,
  просроченные, непроверяемые.
- Защита собственных правил продукта от ослабления (`--base`): понижение уровня и удаление
  правила ловятся.
- `--no-exec`: команды из правил чужого репозитория не исполняются.
- Вывод для CI: JUnit, SARIF, GitLab Code Quality, markdown.

## Границы, которые нужно показывать честно

| Граница | Что происходит | Как закрывать |
|---|---|---|
| Проверки наличия слов | `must_contain` обходится упоминанием в комментарии | Поведенческие тесты, структурные правила; хрупкие — только `warn` |
| Затенение | Продукт объявляет своё правило с именем корпоративного и делает его пустым — нарушение скрыто | Эффективный файл ДКА |
| Удаление `extends` | Корпоративные правила молча исчезают из проверки | Эффективный файл ДКА |
| Самовольное исключение | Override со ссылкой на несуществующий ADR принимается | Реестр исключений ДКА + эффективный файл |
| Разбор импортов | `dependency_direction` — текстовая эвристика, не AST | Для JVM — `archunit` |
| Переименование зависимости | `deny_dependency` не видит `lp = { package = "left-pad" }` в Cargo.toml | Дополнительный `must_not_contain` по `package = "<имя>"` в манифестах |
| Экосистемы техрадара | `deny_dependency` читает только Cargo.toml, pom.xml, requirements.txt | Расширение или `command_succeeds` со своим сканером |
| Агрегация по флоту | Отчёт по одному продукту; сводку по флоту Spine не строит | `session.py fleet report` на встрече, ночная джоба в пилоте |
| Позиция продукта | Однопользовательский инструмент | Использовать как CLI в CI; владение правилами — процессом ДКА |

Проверка ослабления защищает собственные правила продукта, но не унаследованные корпоративные.
Поэтому корпоративный слой в пилоте проверяется по эффективному файлу, который собирает ДКА
(`session.py effective`), а не по продуктовому файлу.

## Результат дуэли второй версии (прогон Qwen Code + DeepSeek V4 Flash)

Чистая LLM — 12 из 12 в обоих прогонах, Spine Core — 10 из 12 за 0,2 с. Гипотеза о том, что
LLM поддастся уговорам, инъекции или длинному файлу, на том наборе опровергнута. Движок выиграл
только по скорости. Третья версия проверяет эту гипотезу на более сложных случаях.

## Не проверено

- LLM-часть Spine: рубрики, судья, реальный handoff в кодовый харнесс.
- Дуэль с настоящей LLM: подсчёт проверен, но результат LLM-стороны зависит от модели и
  получается только прогоном у архитектора.
- Мост к ArchUnit (нужна JVM).
- Производительность на больших реальных репозиториях банка.
- Банковский hardening-профиль (закрытая часть продукта).

## Ответы на трудные вопросы

**«Это готово для промышленного контура банка?»**
Движок проверок зрелее, чем обычно бывает у молодого проекта: зелёные тесты, воспроизводимые
кейсы, защита от ослабления правил. Банковский hardening и LLM-часть ещё нужно проверить —
пилот ровно для этого. Результаты пилота (правила, процесс исключений, гейт) переносимы
на любой движок.

**«Агент же может сам написать правила — зачем архитектор?»**
Правила, написанные агентом, — такой же сгенерированный артефакт, как architecture.md.
Кто-то должен решить, какие из них надёжны. Это и есть новая роль архитектора.

**«Команды будут обходить гейт»**
Поэтому правила и исключения живут в репозиториях ДКА, гейт — отдельная джоба ДКА в Jenkins,
а слияние в Bitbucket требует её статуса. На встрече это показано в `bypass`.

**«А если всё будет красным?»**
Старый долг фиксируется baseline, первые недели — только предупреждения, в блокирующий режим
переходят только надёжные правила.

**«Почему не просто скилл с моими скриптами?»**
Сила проверок одинакова. Разница — в принудительности, версиях стандарта, наследовании и отчёте
по флоту; часть этого Spine даёт готовым, часть (владение правилами) даёт процесс ДКА.

## Неполадки

| Симптом | Причина | Решение |
|---|---|---|
| «файл не содержит правил» | Пустой список правил и нет `extends` | Добавьте хотя бы одно правило |
| Правило не срабатывает на очевидном нарушении | glob не совпадает с путями или фигурные скобки в glob | Список в glob; проверить через selftest |
| `^` не находит строку | Паттерн применяется ко всему файлу | Добавить `(?m)` |
| Паника с «Broken pipe» | Вывод arch-be обрезан через `head` | Не обрезать вывод конвейером; использовать `--top` |
| Долгая проверка | Debug-сборка или огромный каталог | Release-сборка; исключить vendor/generated через `exclude_glob` |
