# Прогон четвёртой версии навыка (spine-wow-session v4)

Живой прогон **четвёртой версии скилла** в TUI Qwen Code 0.24.4: семь коротких реплик
архитектора, чистая папка, **Python 3.11.8**, `arch-be 0.3.8`, **cargo 1.98** для контрактных
тестов. Главная проверка — сдвиг v4: Spine Core не анализатор кода, а **судья над проверками**,
поэтому смысловое требование проверяется исполняемым контрактом, а не регуляркой.

Сам скилл лежит рядом: [`../skill-v4/`](../skill-v4).

## Что проверяла четвёртая версия

| Замысел v4 | Что показал прогон |
|---|---|
| Контрактный тест ДКА `assets/contracts/idempotency/` через `command_succeeds` | Агент добавил правило `idempotency_contract` (§4.1) и на `check --exec` получил **реальную находку** на `payments-arm-a`: «повторный вызов с тем же ключом списал дважды», хвост вывода теста приведён в отчёте |
| Контракт применяется только там, где есть что проверять | `cards-product` контракт честно пропустил: `authorize` не найдена → «не применимо», exit 0 |
| Команды исполняются только из слоя ДКА (`$DKA_HOME`) | правило ссылается на `$DKA_HOME/contracts/…`, `lint-rules` это проверяет; `DKA_HOME` подставляет сам `session.py` |
| Дуэль из пяти столбцов | Spine на шаблонах **11/16**, Spine + контракт **15/16**, чистая LLM 16/16, LLM + Spine 16/16, маршрутизация 16/16 |
| Гейт ДКА и его неизменяемость | `ci-redteam`: шаблон отбил 7 атак из 7; схема «гейт в продукте» пропускает 2 |

## Семь реплик архитектора (дословно)

```
1. Мой стандарт лежит в context/standard/, репозитории перечислены в session.yaml.
   Покажи, что у меня нарушается.

2. Регулярками смысловые требования не проверить. Можно ли проверять идемпотентность
   по-настоящему — запуском теста?

3. Проверь, что реестру правил можно доверять: точность и надёжность.

4. Покажи стандарт как продукт: выпусти новую версию слоя и покажи, кто её ещё не применил.

5. Хочу, чтобы это проверялось в CI, и чтобы было видно, что гейт не обойти.

6. Теперь подготовь дуэль: пять столбцов, включая Spine с контрактным тестом.
   Наборы для LLM я прогоню сам в чистых каталогах.

7. Ответы LLM готовы в reports/duel/. Посчитай дуэль, проверь готовность
   и собери раздатку к встрече.
```

## Дуэль: пять столбцов на 16 случаях

LLM-наборы (`kit-llm`, `kit-combo`) прогонялись по три раза в чистых копиях, отдельными сессиями.

| Показатель | Spine: шаблоны | Spine: шаблоны + контракт | Чистая LLM | LLM + Spine Core | Маршрутизация (расчёт) |
|---|---|---|---|---|---|
| Верно решённых из 16 | 11 | **15** | 16 | 16 | 16 |
| Пропущенные нарушения | 3 | **0** | 0 | 0 | 0 |
| Ложные срабатывания | 2 | 1 | 0 | 0 | 0 |
| Одинаковый вердикт во всех прогонах | 16 из 16 | 16 из 16 | 16 из 16 | 16 из 16 | — |
| Время на прогон, с | 0.2 / 0.2 | 10.0 / 7.2 | 420 / 240 / 240 | 210 / 240 / 104 | — |

Что это даёт на встрече:

* контрактный тест **закрыл все три пропуска** текстового слоя и поднял движок с 11 до 15 из 16 —
  то есть слабость была не в Spine, а в выбранном типе проверки;
* осталась ровно одна ошибка — **C11**: `f64` в метриках задержки. Поведенческим тестом вопрос
  «деньги это или не деньги» не решается: нужна модель или соглашения об именах;
* контракт стоит 7–10 с на репозиторий после прогрева кэша cargo (первый прогон — скачивание
  `thiserror`), против 0.2 с у регулярки и 104–420 с у LLM. Это и есть цена сильной проверки;
* у LLM в этом прогоне 16 из 16 при полной стабильности — то есть на синтетических случаях
  сильная модель решает всё; разница между участниками проявляется в **повторяемости, скорости
  и в управлении правилами**, а не в этом частном счёте.

## Что агент честно вынес в отчёт

1. **Шапка `reports/check.md` врёт:** печатает «режим `--no-exec`», хотя контракт реально
   исполнялся. Строка жёстко зашита в `cmd_check`. Агент предложил поправить `session.py`
   (одна строка, вычислять из `--exec`), но сам механизм не трогал.
2. **§4.1 попадает в отчёт дважды** — текстовое правило и контракт дают две находки; предложено
   оставить текст ранним сигналом, а вердикт считать по контракту.
3. **Контракт нельзя переводить в `block`** — у него нет примеров `bad/good/bypass` для selftest,
   и `lint-rules` это фиксирует. Как только примеры появятся, гейт `armA` станет красным.
4. **В раздатку уехал реестр 2026.1 (7 правил), а релиз — 2026.2 (9 правил):** `pack` берёт
   `work/CONSTRAINTS.corp.yaml`, а выпущенная версия живёт в `sandbox/corp/`. Агент предложил
   либо синхронизировать реестр и пересобрать пакет, либо явно проговорить это на встрече.
5. **`ci-template/contracts/` содержит штатный контракт скилла** (фикстуру дуэли) — для реальных
   сервисов его нужно заменить адаптированным, иначе гейт покраснеет не по делу.
6. **C11 остаётся ошибкой** и в столбце с контрактом — это граница метода, а не дефект прогона.

## Технические замечания по прогону

* Первый `check --exec` собирает временный крейт (`cargo`), кэш общий через `DKA_CARGO_TARGET`;
  последующие прогоны — 7–10 с.
* Каталоги сборки `target/` (125 МБ в `sandbox/mutation/`) из пакета **исключены** — в пакете
  остаются исходники экспериментов, манифесты и JSON-результаты, но не бинарные артефакты cargo.
* `DKA_HOME` переопределять не нужно и не следует: наборы и `duel score` работают со штатным
  контрактом скилла.
