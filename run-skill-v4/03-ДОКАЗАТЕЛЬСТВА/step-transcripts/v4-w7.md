## Как CI устроен

Разворачивается в репозиторий ДКА `dka-ci` — не в продукты:

```
dka-ci/
  ci/                       Jenkinsfile, dka-gate.sh, build_effective.py
  corp/CONSTRAINTS.corp.yaml      выпущенный слой (у нас 2026.2)
  exceptions/<продукт>.yaml       одобренные исключения
  baselines/<продукт>.json        baseline долга (brownfield)
  contracts/                      контрактные тесты ДКА (command_succeeds)
```

Джоба ДКА (Jenkinsfile) по вебхуку Bitbucket на PR: всегда берёт скрипт из **checkout ДКА** (`.dka/ci/dka-gate.sh`), `arch-be` скачивается из Nexus с проверкой sha256, результат публикуется как JUnit + артефакты (`corp.json`, `effective-corp.yaml`, `corp-junit.xml`). В Bitbucket: обязательная сборка со статусом этой джобы перед слиянием и права на ветку `dka-ci` — только у владельцев ДКА.

Две ступени `dka-gate.sh`:

1. **Решающая** — эффективный файл собирается только из реестра ДКА и реестра исключений ДКА (`build_effective.py`: исключение без ADR/срока или длиннее 180 дней роняет гейт с ошибкой конфигурации), проверка корпоративного слоя **с исполнением контрактов ДКА**, опционально baseline. Продуктовый `CONSTRAINTS.yaml` в этой проверке не участвует — поэтому его правкой ничего не выключить.
2. **Информативная** — собственные правила продукта с `--no-exec`; решающее в них только ослабление (`--base`: понижение уровня или удаление правила → `rule_weakened`).
