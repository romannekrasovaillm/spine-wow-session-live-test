# Требования стандарта: Стандарт платёжного ядра v2

Источник: Confluence (демо-экспорт), `context/standard/payment-core-standard.md`.
Сгенерировано агентом из текста стандарта, проверено архитектором: **нет**.

Классы проверяемости:
- **A** — проверяется автоматически по коду, зависимостям или конфигурации;
- **B** — частично: нужен тест или анализ структуры кода;
- **C** — только человеком.

| ID | Требование | Пункт стандарта | Класс | Как проверить | Правило |
|---|---|---|---|---|---|
| R-01 | Денежные суммы не хранятся в типах с плавающей точкой | §2.1 | A | Текстовый поиск `f32`/`f64` в исходниках | `no_float_for_money` |
| R-02 | Ошибки домена описываются типизированно (`thiserror`) | §3.2 | B | Наличие зависимости `thiserror`; структурно полное отсутствие `Box<dyn Error>` текстом не проверяется | `thiserror_for_errors` |
| R-03 | `anyhow` и `Box<dyn Error>` запрещены | §3.2 | A | Запрет зависимости `anyhow` + переименованное подключение `package = "anyhow"` | `tech_radar_hold`, `tech_radar_renamed` |
| R-04 | Авторизация платежа идемпотентна по ключу | §4.1 | **B** | Поведенческий контрактный тест ДКА (`command_succeeds`, только `--exec`); наличие слова `idempotenc` — хрупкая замена, не доказательство | `idempotency_contract` (вердикт), `authorize_idempotent` (ранний сигнал) |
| R-05 | Библиотеки из зоны HOLD (`anyhow`, `left-pad`) не используются | §5.1 | A | Запрет зависимости + переименование | `tech_radar_hold`, `tech_radar_renamed` |
| R-06 | Каждый сервис публикует метрики по стандарту наблюдаемости | §6.1 | **C** | Только человеком: содержательность метрик автоматом не проверяется | `observability_standard` (unverifiable) |

## Замечания агента к стандарту (требуют решения архитектора)

1. **R-03 и R-05 пересекаются:** `anyhow` назван и в §3.2 (ошибки), и в §5.1 (техрадар).
   Одно нарушение `anyhow` попадёт в отчёт дважды — по правилу ошибок и по правилу техрадара.
   Нужно решить, какой пункт считать основным.
2. **R-04 не сводится к тексту.** Требование проверено поведенческим контрактом ДКА
   (`sandbox/dka-contracts/contracts/idempotency/`, демо-версия для пилота — репозиторий `dka-ci`).
   Контракт пришлось написать под фактический интерфейс репозиториев: у armB есть ключ
   (`PaymentProcessor::authorize(payment, key)`), у armA ключа нет вовсе — для него требование
   выражено как безопасность ретрая. Готовый контракт скилла
   (`assets/contracts/idempotency/`) на этих репозиториях не работает: он написан под
   интерфейс `Processor`/`Payment: Default`/`Receipt` сгенерированных кейсов дуэли, а его
   временный манифест не содержит `thiserror`, из-за чего исходники продукта не компилируются.
   Вывод: контракт API — часть стандарта, и для каждого сервиса он пишется заново.
3. **§6.1 «по стандарту наблюдаемости»** ссылается на документ, которого нет в `context/standard/`.
   Пока это `unverifiable`, владелец — ДКА наблюдаемости.
